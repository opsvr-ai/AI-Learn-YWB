LLM Basics

大语言模型基础

理解大语言模型（Large Language Model）的核心概念，是掌握所有AI工具使用方法的基石。

通俗理解：想象一座巨型图书馆里有一位"超级图书管理员"，她不仅读过馆里的每一本书、每一篇文章、每一段代码，还能在几秒钟内理解你的问题，从海量知识中提炼出你最需要的答案。这位"超级图书管理员"就是大语言模型。

技术定义：大语言模型（Large Language Model，简称LLM）是一种基于深度学习的人工智能模型，通过在数以万亿计的文本数据上进行训练，学习人类语言的模式、结构、知识和推理方式。它采用"自回归预测"的方式工作——根据上文逐词（严格说是逐token）预测下一个最可能出现的词，从而生成连贯、有意义的文本。

与传统软件的区别：传统软件是"规则驱动"的——开发者编写明确的if-else逻辑，软件按固定流程执行。大语言模型则是"模式驱动"的——它从数据中学习规律，面对新问题时灵活推理，不需要人工预设每一条规则。

一个具体例子：你向模型输入："请用通俗的语言解释什么是机器学习。"模型经过内部计算后输出："机器学习就像是教小孩认动物——你给她看很多猫和狗的照片，告诉她哪个是猫哪个是狗，慢慢地她自己就能分辨了。计算机也是这样，我们给它大量数据让它'练习'，它就能学会识别模式。"——模型并不是从数据库中"检索"到这段答案，而是基于对语言的理解逐词"生成"出来的。

♦

Token（词元）

大模型处理文本的最小单位，可以理解为一个"词片"。比如"人工智能"这个词可能被拆成2～3个token。一般来说，中文约1.5个字符 = 1个token，英文约0.75个单词 = 1个token。Token数量决定了API调用成本和上下文容量上限，是使用AI工具时必须关注的基础概念。

▦

上下文窗口（Context Window）

可以把上下文窗口理解为模型的"短期记忆容量"——模型在一次对话中能"看到"的最大文本量（包含你的输入和模型的输出）。不同模型的窗口大小差异很大，从4K到100万+tokens不等。当对话超出窗口限制时，你需要开启新对话或对前面的内容做摘要压缩。

♧

Temperature 与 Top-P

Temperature（温度）控制输出的随机性：低温度（0～0.3）让模型回答更精确、一致，适合写代码和查事实；高温度（0.7～1.0）让回答更有创意和多样性，适合头脑风暴。Top-P（核采样）是另一种控制多样性的方式，通常与Temperature配合使用。

大模型的训练是一个复杂的多阶段过程，可以类比为一个人的成长教育历程：

图：大模型训练的四个阶段——数据 → 能力 → 对齐 → 进化

  1. 预训练（Pre-training）——"上完所有学"

    让模型在海量文本数据（互联网网页、书籍、论文、代码等）上自主学习语言模式。这一阶段耗时最长、算力消耗最大。模型学会了语法、事实知识和基本的推理模式，但还不会"对话"——它只会续写文本。

  2. 指令微调（Instruction Fine-tuning）——"专业训练"

    用高质量的人工标注数据（包含明确的指令和对应的理想回答）对模型进行有监督训练，让模型学会"听懂人话"——理解指令意图并按指令要求完成任务，而不是简单地续写文本。

  3. RLHF（人类反馈强化学习）——"师傅带徒弟纠正"

    人类评估员对模型的多个回答进行打分排序，模型通过这些反馈学习什么样的回答是"好"的——更有用、更安全、更符合人类价值观。这就像师傅指出徒弟哪里说得好、哪里需要改进。

  4. 后训练（Post-training）——"持续精进"

    在模型投入使用后，通过用户反馈、新数据加入、安全对齐等手段不断优化模型表现。最新的大模型（如Claude 4、GPT-4o）都经过了大量的后训练优化。

✓

优势

  • 海量知识：模型训练涵盖了几乎所有公开领域的基础知识，能快速回答跨学科问题。
  • 多语言能力：支持数十种语言的理解与生成，中英文切换自如。
  • 推理能力：不仅仅是"查资料"，还能进行逻辑推理、归纳总结、方案设计。
  • 创造力：能生成全新的文本内容，从文案到代码到创意方案。
⚠

局限

  • 幻觉（Hallucination）：模型有时会"一本正经地胡说八道"，生成看似合理但事实错误的内容。
  • 知识截止日期：模型的知识停留在训练数据截止的时间点，不知道之后发生的事。
  • 数学计算弱点：纯粹的数字计算并非模型强项，复杂数学建议结合代码执行工具。
  • 偏见问题：训练数据中的人类偏见可能被模型学习并放大，需要警惕。
如何应对局限？结合外部工具（Function Call / MCP协议）让模型调用计算器、搜索引擎、数据库来弥补不足；对关键输出进行人工审核；使用RAG（检索增强生成）技术为模型补充实时知识——这些都是我们日常使用AI工具时可以采用的实用策略。
API Config

模型接入配置基础

在使用 Hermes-Agent、Claude Code 或任何 AI 工具之前，你都需要了解几个关键的配置概念：接口类型、Base URL、API Key、模型名。这一节帮你彻底搞懂它们，不再对着配置界面发懵。

目前主流的 AI 模型接入方式有两种接口标准。简单说，接口就是"AI 服务的通信协议"——你的程序按照这个协议发送请求，AI 服务按照这个协议返回结果。了解它们的区别，是配置一切 AI 工具的第一步。

🔌

OpenAI 兼容接口

由 OpenAI 最早定义、后被行业广泛采用的接口格式，已成为事实上的行业标准。

核心特征：

  • 聊天接口路径：/chat/completions
  • 认证方式：Authorization: Bearer <API_KEY>
  • 大多数国产模型都兼容此格式
  • Hermes-Agent 使用此接口

类比：就像 USB-A 接口——不是最先进的，但因为用得太广，几乎所有设备都支持。

🔑

Anthropic 原生接口

由 Anthropic 为 Claude 系列模型定制的专有接口，在工具调用和长上下文方面有独特设计。

核心特征：

  • 认证方式：x-api-key: <API_KEY>
  • 使用 Messages API 消息格式
  • 原生支持更丰富的工具调用能力
  • Claude Code 使用此接口

类比：就像 Apple Lightning 接口——专有标准，但在自家生态内体验最好。

🏢 公司内网的实际情况

公司 AI Gateway 同时支持 OpenAI 兼容接口和 Anthropic 原生接口，根据使用场景选择：

🔌 OpenAI 兼容接口

适用场景：日常办公聊天、文档处理、通用问答
代表工具：Hermes-Agent

🔑 Anthropic 原生接口

适用场景：代码开发、深度推理、复杂编程任务
代表工具：Claude Code

Gateway 在后端统一对接各种模型，前端提供两种接口格式供不同工具选用。你不需要关心 Gateway 内部如何"翻译"——只需根据使用的工具选对接口类型即可。

一句话记住 日常使用中你基本不需要关心底层接口细节——配置工具时会明确告诉你选哪个。记住：编码开发场景用 Anthropic 接口（Claude Code），日常办公场景用 OpenAI 兼容接口（Hermes-Agent）。接口地址指向 Gateway，模型名告诉 Gateway 你想用哪个模型。

Base URL（基础地址）就是 AI 服务的网络地址。你的程序通过这个地址找到 AI 服务在哪里，就像寄快递需要知道收件地址一样。

🏠

格式与构成

Base URL 是一个标准的 HTTP 地址，通常由三部分组成：

协议 + IP/域名 + 端口
例如：http://7.24.28.9:28080/v1

  • http:// — 通信协议
  • 7.24.28.9 — 服务器 IP 地址
  • :28080 — 端口号（AI 服务监听的"频道"）
  • /v1 — API 版本路径（表示使用 v1 版接口）
🌐

常见 Base URL 示例

服务Base URL
OpenAI 官方https://api.openai.com/v1
Anthropic 官方https://api.anthropic.com
公司内网 Gatewayhttp://7.24.28.9:28080/v1

注意：公司内网地址使用的是 HTTP 而非 HTTPS，且 IP 可能随网络调整而变化。

💡 关键理解 Base URL 是所有 API 请求的前缀。比如完整的聊天接口地址就是 Base URL + /chat/completions = http://7.24.28.9:28080/v1/chat/completions。你不需要手动拼接——配置工具时填好 Base URL，工具会自动在后面加上对应的接口路径。

API Key（密钥）是一串用于验证你身份的字符。就像你的工卡——刷卡才能进门；API Key 就是你访问 AI 服务的"电子工卡"。

🔒

为什么需要 API Key？

AI 服务不是免费公益项目——每次调用都需要计算资源。API Key 起到三个关键作用：

  • 身份验证——你是谁？
  • 权限控制——你能用哪些模型？
  • 用量统计——你用了多少 Token？
💳

API Key 长什么样？

通常是一串由字母和数字组成的随机字符串，例如：

sk-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

OpenAI 格式的 Key 通常以 sk- 开头（"secret key"的缩写）。公司内网 Gateway 的 Key 由平台统一生成和管理。

🚨

安全注意事项

  • ❌ 不要截图发给别人
  • ❌ 不要提交到 Git 仓库
  • ❌ 不要在即时通讯中明文传输
  • ✅ 配置文件用占位符替代后分享
  • ✅ 泄露后立即在平台重置

🔑 API Key 在请求中怎么用？

你的程序每次向 AI 服务发请求时，都会在 HTTP 请求头中带上 API Key。以 OpenAI 兼容接口为例：

Authorization: Bearer sk-your-api-key-here

整个过程对你是透明的——你只需在配置文件中填好 Key，工具会自动处理后续的认证逻辑。

💡 关键理解 不要把"API Key"和"登录密码"混为一谈。API Key 是程序间通信的凭证，不是网页登录用的。你不需要记住它——把它当作一个"配置文件参数"即可。需要申请时，参考 API Key 申请指南。

Model Name（模型名称）告诉 AI 服务你想使用哪个具体的模型来处理你的请求。同一个 Base URL 下通常有多个模型可用——就像一座写字楼里有很多家公司，门牌号（Base URL）只能带你到楼门口，公司名（Model Name）才能找到你要去的那一家。

🧠

模型名的作用

在 API 请求中，模型名是你必须指定的参数之一。Gateway 根据这个参数决定把请求转发给哪个模型引擎。

{ "model": "Qwen3.6-35B-A3B", "messages": [...] }

每个请求中都需要指定 model 字段

📜

常见模型命名规则

模型名通常包含厂商、版本、参数规模等信息：

gpt-4oOpenAI 多模态旗舰
claude-sonnet-4-6Anthropic Claude 4 系列
deepseek-v3DeepSeek 最新版
Qwen3.6-35B-A3B常用办公聊天推荐

💡 配置时怎么选模型？

如果你是第一次配置 AI 工具，不需要自己去"挑选"模型——以下是简单实用的选择指南：

  • 日常办公聊天（写邮件、写报告、问答）：推荐 Qwen3.6-35B-A3B
  • 代码开发（编程、调试、Code Review）：推荐 Claude 系列
  • 中文长文档处理（翻译、摘要、分析）：推荐 Qwen 或 DeepSeek 系列
  • 不确定选哪个？直接用平台推荐的默认模型，后续根据效果再调整
💡 关键理解 模型名只是一个字符串参数——你不需要下载或安装任何东西。AI 服务端已经部署好了所有模型，你只需要告诉它"我要用哪个"。配置错模型名不会造成安全问题，只是服务端会返回"模型不存在"的错误。如果你换了模型名，同一个问题可能得到完全不同的回答——因为不同的模型有不同的"知识面"和"思维方式"。

这四个概念不是孤立的，它们共同构成了"让程序找到并调用 AI 服务"的完整链路。用一个生活类比来串联：

图：四个配置概念构成"找到服务 → 验证身份 → 选择引擎 → 获得结果"的完整链路

在 Hermes-Agent 中实践

回顾 Hermes-Agent 的配置流程——hermes setup 命令会让你依次填入三个信息，现在你应该完全理解它们的含义了：

  1. Base URL → AI Gateway 的地址，如 http://7.24.28.9:28080/v1
  2. API Key → 你在平台上申请的密钥，如 sk-xxxx...
  3. Model Name → 你想用的模型，如 Qwen3.6-35B-A3B

（接口类型不需要你选——Hermes-Agent 默认使用 OpenAI 兼容接口，因为公司 Gateway 封装的正是这种格式。）

Prompt Engineering

提示词工程

提示词是与大模型沟通的语言。写好提示词，是高效使用AI的第一步。

★

角色设定（Role Prompting）

在提示词开头为模型设定一个具体角色和背景，能显著提升输出的专业性和针对性。

示例："你是一位拥有10年经验的资深后端工程师，精通Python和分布式系统设计。请帮我..."

角色越具体，回答越精准。你可以设定角色的身份、经验年限、专业领域、甚至性格特点。

☰

结构化指令（Structured Instructions）

用清晰的章节分隔你的提示词，让模型准确理解你的需求层次。

推荐结构：
## 背景 → ## 任务 → ## 要求 → ## 输出格式

这种方式比一段长长的自然语言描述有效得多——它避免了信息的混杂和遗漏。

♦

Few-shot Prompting（少样本提示）

在提问前先给出2～3组"输入→理想输出"的示例，让模型理解你的格式和风格期望。

示例："将以下口语转为正式书面语。示例1：'这事儿搞定了'→'此事已完成'。示例2：'有点难'→'存在一定难度'。现在请转换：'我觉得还行'"

★

Chain-of-Thought（思维链）

引导模型逐步推理，而不是直接给出答案。尤其适合数学题、逻辑推理和多步骤问题。

在提示词末尾加上一句 "让我们一步一步思考。"就能激活模型的逐步推理能力，大幅提升复杂问题的准确率。

对于代码调试，还可以要求模型"先分析Bug可能的原因，再给出修复方案"。这比直接要求"修Bug"效果好得多。

▦

结构化输出

明确指定输出格式，让模型按照你的要求组织信息。

你可以要求模型输出为JSON、Markdown表格、待办清单、甚至特定代码格式。例如："请用Markdown表格列出这三种方案的优缺点"或"请以JSON格式返回结果"。结构化输出不仅让结果更易读，还能直接对接自动化流程。

♧

思维树（Tree of Thoughts）

同时探索多条推理路径，比较各路径的优劣，最终选择最优解。是思维链的升级版。

使用方式：让模型对同一问题生成3种不同的解决思路，分别评估每种思路的可行性，最后给出综合推荐。适合复杂决策场景。

✎

在 Hermes-Agent 中

Hermes-Agent 提供了便捷的对话界面，你可以在输入框中直接编写结构化的提示词与AI交互。所有提示词技巧（角色设定、结构化指令、Few-shot、思维链等）都可以直接应用。

实用技巧：将常用且效果好的提示词保存为模板，下次遇到类似任务时微调即可，大幅提升工作效率。公司内部也可以逐步建立团队共享的提示词模板库。

⌨

在 Claude Code 中

Claude Code 将提示词工程提升到了一个新的层次：

  • CLAUDE.md 相当于持久化的系统提示词——你可以在其中定义项目规范、编码风格、技术栈偏好，Claude Code每次启动都会自动读取并遵循。
  • 任务级提示词 就是你每次提出的开发需求——越是清晰、结构化地描述需求，Claude Code越能准确执行。
核心心法：好的提示词不是一次写成的——把它当作与AI的对话迭代过程：第一版提示词 → 观察输出 → 发现不足 → 调整提示词 → 获得更好的输出。反复迭代2～3轮，你就能找到最适合当前任务的提示词方案。记住：提示词是你和AI之间的"沟通协议"——协议越清晰，协作越高效。
Function Call

函数调用 (Function Call)

让大模型不仅会"说"，还会"做"——这是AI从聊天工具进化为智能助手的关键能力。

想象一下，你有一个非常聪明的顾问，但他只能动嘴、不能动手。你问他"今天北京天气怎么样？"，他能滔滔不绝地讲天气预报原理，但就是无法告诉你此刻外面是晴是雨——因为他没有"查天气"的能力。

Function Call（函数调用）就像给这位顾问配了一个万能遥控器。你说"帮我查北京天气"，他按遥控器上的"天气预报"按钮，电视上立刻显示实时数据。顾问看了数据，转身对你说："北京今天25度，晴天，适合户外活动。"

这个"遥控器"就是 Function Call——让大模型能够实际执行操作，而不仅仅是生成文字。它是AI从"会聊天"到"能办事"的分水岭。

Function Call 的本质

大模型不是自己去调接口、查数据库、发邮件，而是输出一个"调用指令"（JSON格式），由你的程序去执行，执行结果再还给模型。模型是大脑，Function Call 是手。大脑负责思考和决策，手负责实际操作。

技术小贴士：严格来说，大模型本身并不知道它"调用了一个函数"。它只是按照训练时学到的格式，输出一段结构化的JSON文本。是你的程序识别了这段JSON，执行了对应的函数，然后把结果拼回对话中。整个过程对用户完全透明。

Function Call 的完整流程像是一场精心编排的接力赛：用户发起请求，模型和服务程序交替传递信息，最终呈现给用户一个"好像AI什么都会"的体验。

  1. 用户发送请求 + 可用函数列表

    用户提问时，程序同时把一份"函数菜单"发给模型。菜单上写着每个函数的名称、功能描述和参数要求。比如：get_weather(city: string) —— 查询指定城市的天气。

  2. 模型判断是否需要调用函数

    模型分析用户意图：这个问题我能直接回答吗？还是需要借助工具？如果用户问"1+1等于几"，模型直接回答；如果问"北京现在多少度"，模型意识到需要调用 get_weather。

  3. 模型输出函数调用 JSON

    模型不输出自然语言，而是输出一段结构化指令：{"name": "get_weather", "arguments": {"city": "北京"}}。注意——此时模型还没有拿到任何真实天气数据。

  4. 程序执行函数，获取真实数据

    你的程序（不是模型）收到这段JSON后，去真正调用天气API，拿到真实结果：{"temperature": 25, "condition": "晴"}。

  5. 执行结果返回模型

    程序把API返回的真实数据作为新的上下文，追加到对话中，再次发给模型。

  6. 模型结合结果生成最终回复

    模型拿到真实数据后，生成自然语言回复："北京今天25度，晴天，体感舒适，适合户外活动。"用户看到的就是这个最终答案。

图：Function Call六步交互流程——模型不自己调接口，而是输出调用指令，由程序代为执行

整个过程对用户是透明的——用户只看到"北京今天25度，晴天"，看不到中间的JSON交互。就像你点外卖，你只关心饭到了没，不需要知道骑手的GPS坐标和后厨的订单系统如何运作。

Function Call 的应用范围极广，以下是最典型的四类场景。每个场景都遵循同样的模式：用户用自然语言提需求，AI自动调用对应工具，返回结构化结果。

📊

查询数据库

用户说"上个月销售额多少？"→ 模型自动生成SQL并调用 query_database() → 返回真实数字。无需用户会写SQL。

🔗

调用外部API

用户说"帮我查这个快递到哪了"→ 模型调用 track_package() → 返回实时物流状态。连接成千上万个API。

📄

操作文件

用户说"把这份Excel转成CSV"→ 模型调用 convert_file() → 返回下载链接。文件格式转换、批量重命名等都能搞定。

🔔

发送通知

用户说"提醒我下午3点开会"→ 模型调用 create_reminder() → 日程创建成功。打通日历、邮件、短信等通知渠道。

核心优势：用户不需要知道数据库在哪、API怎么调、文件系统是什么。只要用自然语言说出需求，Function Call 就负责把"人话"翻译成"机器指令"，再把机器结果翻译回"人话"。

Function Call 定义了"模型能调用函数"这个能力。但它只解决了"能不能"的问题，没有解决"怎么统一"的问题。现实情况是每个工具的接口都不一样——连接MySQL是一套写法，PostgreSQL是另一套，公司内部API又是另一套。

这就是 MCP（Model Context Protocol）要解决的问题。MCP 定义了一套标准协议——就像USB-C统一了充电接口——让任何AI应用都能用同样的方式连接任何工具。

一句话总结关系

Function Call = 大模型的"手"，让AI有了执行操作的能力。
MCP = 让这只手能拿任何工具的"标准接口"，不用每换一个工具就重新设计一只手。

MCP

模型上下文协议 (MCP)

MCP 是AI应用的"USB-C接口标准"——让任何AI客户端都能无缝对接任何工具和数据源，告别逐个定制的时代。

想象一下——如果每个品牌的手机都需要自己专用的充电线，你的桌面会是怎样的灾难？直到 USB-C 出现，一根线充所有设备，世界清净了。

MCP（Model Context Protocol）在AI领域做的事情，和USB-C在充电领域做的事情一模一样：统一了"AI如何连接外部工具"的接口标准。

维度MCP 出现之前MCP 出现之后
连接方式每个AI应用 × 每个工具都要单独写对接代码（N×M 问题）任何AI应用（MCP Client）↔ 标准协议 ↔ 任何工具（MCP Server）
开发成本每接一个新工具，从头写适配层工具提供方只需实现MCP Server，所有AI客户端自动兼容
生态扩展封闭、碎片化，每个平台各自为战开放、可复用，社区共享MCP Server，即装即用

MCP 的背景

MCP 由 Anthropic 于2024年底提出并开源，是当前AI领域最受关注的开放协议之一。它借鉴了 LSP（Language Server Protocol，IDE领域统一编程语言支持的协议）的设计思想。Claude Code 和 Hermes-Agent 都深度集成了 MCP。

MCP 采用经典的客户端-服务器（Client-Server）架构，结构清晰、职责分明：

⌨

MCP Client（客户端）

AI应用端，如 Claude Code、Hermes-Agent。它负责发起连接请求、发现可用工具、调用工具、读取资源。Client 是"提问者"和"使用者"。

举例：你在 Claude Code 里说"帮我查数据库"，Claude Code（Client）就去找数据库 MCP Server 要数据。

🔧

MCP Server（服务端）

工具提供端，如文件系统Server、数据库Server、浏览器Server。它暴露三种能力：Tools（可调用的操作）、Resources（可读取的数据）、Prompts（提示模板）。

举例：数据库 MCP Server 暴露 execute_sql 工具和 schema 资源，Client 调用它来查询数据。

🛸

Transport（传输层）

通信通道。支持两种方式：stdio（标准输入输出，用于本地进程间通信）和 HTTP/SSE（用于远程服务通信）。本地工具用 stdio，远程服务用 HTTP。

举例：你本机的文件系统 MCP Server 通过 stdio 与 Claude Code 通信；公司内网的API Server 通过 HTTP 连接。

图：MCP Client-Server 架构——标准协议连接任何客户端与任何服务端，告别 N×M 集成困境

每个 MCP Server 都可以暴露三类能力，我们用图书馆作为类比来理解：

📚

Resources（资源）

暴露数据——文件内容、数据库记录、API响应。模型可以"读取"这些数据。Resources 是只读的、结构化的数据入口。

类比：图书馆的书架

走到书架前，找到想要的资料，翻阅内容。

⚙

Tools（工具）

暴露操作——执行SQL查询、发送邮件、创建文件、调用API。模型可以"调用"这些操作。Tools 会改变外部世界状态。

类比：图书馆的电脑

可以在电脑上检索书目、预约借书、查询馆藏位置。

💬

Prompts（提示模板）

暴露专业知识——"代码审查"模板、"翻译"模板。帮助用户快速开始专业任务，不用从头写Prompt。

类比：图书馆的参考咨询台

图书管理员给你推荐书单，帮你少走弯路。

三者的协作关系：一个典型的AI任务往往三者配合使用。比如"分析上周销售数据并生成报告"——先通过 Resources 读取数据库Schema了解表结构，再通过 Tools 执行SQL获取数据，最后用 Prompts 中的"数据分析报告"模板优化输出格式。

MCP 自发布以来，社区和各大厂商已经贡献了大量现成的 MCP Server：

🗃

文件系统 (Filesystem)

安全地读写本地文件和目录。支持创建、读取、编辑、删除、搜索文件操作。

🗃

数据库 (PostgreSQL / SQLite)

查询和分析数据库。AI可以直接执行SQL、读取表结构、分析数据趋势。

🌐

浏览器 (Puppeteer / Playwright)

自动化网页操作。AI可以打开网页、点击按钮、填写表单、截取页面截图。

💻

Git（版本控制）

管理代码仓库。AI可以提交代码、创建分支、查看历史、生成commit信息。

🔍

搜索引擎 (Brave / Google)

搜索网络信息。AI可以实时搜索网页、获取最新资讯，突破训练数据的时效限制。

📦

办公套件 (Drive / Slack)

集成办公工具。AI可以读取云端文档、发送Slack消息、管理日历。

内网应用：公司内网也可以搭建自己的 MCP Server——比如连接内部数据库、运维平台、监控系统，让 Hermes-Agent 和 Claude Code 等所有AI工具都能通过统一的MCP接口直接查询和操作内部系统。一次开发，全平台通用。

这三个概念不是彼此独立的，而是构成了AI能力逐层递进的技术路线：

层级概念解决的问题类比
第一层Function Call定义了"模型能调用函数"这个能力给AI装上了"手"
第二层MCP标准化了"函数如何被发现、描述和调用"的协议让这只手有了"标准接口"，什么工具都能拿
第三层Agent利用 Function Call + MCP，形成自主的目标→规划→执行→验证循环手+标准接口+大脑的自主判断 = 能独立完成复杂任务的智能体

一句话串起三层

Function Call 给了AI"做事的能力"，MCP 给了"做事的标准方式"，Agent 则把这两者整合成"自主完成任务的全流程"。你使用的 Hermes-Agent 和 Claude Code，本质上就是内置了这三层能力的 Agent 产品。

Agent

AI Agent（智能体）

当大模型学会使用工具、制定计划、反思纠错，它就从"回答问题"进化为"完成复杂任务"——这就是 Agent。

要想理解 Agent，可以先看一个类比：普通大模型像图书馆咨询员——你问什么它答什么，答完就结束。而 Agent 像一个项目经理——你给一个目标，它自己制定计划、协调资源、执行步骤、检查结果、修正错误，直到目标达成才停下。

从技术上看，AI Agent 是一个能够感知环境、推理目标、规划行动、使用工具、执行步骤、观察结果、迭代修正的系统。它的核心是一个循环：感知 (Sense) → 思考 (Think) → 行动 (Act) → 观察 (Observe)，不断循环直到目标达成。

Agent = 大模型（大脑）+ 工具调用（手）+ 记忆系统（笔记本）+ 规划能力（计划表）+ 验证机制（质检员）

五个组件缺一不可：大脑负责理解与推理，手负责执行操作，笔记本负责记录上下文，计划表负责拆解任务，质检员负责验证每一步的结果是否正确。

最简单的例子：你问大模型"今天天气怎么样？"——它只能告诉你它不知道。但如果你给大模型装上一个能查询天气的"工具"，再告诉它"用户问天气时就去调用那个工具"——这就成了一个最简单的 Agent。它不再是只靠记忆回答，而是知道自己不知道什么，并主动去获取答案。

Agent 的工作方式像一个升级版的空调恒温器：恒温器感知温度 (Sense)，对比设定温度决定升温还是降温 (Think)，启动压缩机 (Act)，再检查温度变化 (Observe)，反复调整直到温度达到设定值。

图：Agent核心循环——六步形成一个闭环，不断迭代直到目标达成

  1. 感知 (Perceive)

    理解用户的目标是什么，当前环境状态是什么——有哪些文件？项目结构是怎样的？之前做了什么？

  2. 思考 (Reason)

    分析"要做到这个目标需要做什么"，把大目标拆解成若干个小步骤。就像项目经理拿到需求后先分解 WBS（工作分解结构）。

  3. 规划 (Plan)

    制定具体的执行步骤，决定每一步调用哪个工具。先读哪个文件？先运行哪个命令？先搜索什么？

  4. 行动 (Act)

    实际执行：调用工具、读写文件、运行终端命令、搜索代码库。这是"动手"的阶段。

  5. 观察 (Observe)

    检查执行结果：命令成功了吗？返回的数据符合预期吗？文件内容正确吗？这一步没做好的 Agent 会"一条路走到黑"。

  6. 迭代 (Iterate)

    如果结果不符合预期，调整方案重新执行；如果符合预期，继续下一步。这是一次"内省"——Agent 在不断问自己"我做对了吗？要不要换个方法？"

这个循环不是固定的 简单的任务可能一次就搞定，复杂的任务可能循环几十次。关键在于 Agent 能否自主判断"什么时候算完成了"——这个判断力，就来自大模型的推理能力加上清晰的任务定义。

不是所有"AI助手"都是 Agent。Agent 的能力有一个清晰的进阶路径，像游戏里的等级一样：

能力层级 核心特征 典型能力 代表产品
L1 简单响应 一问一答，无工具，无记忆 回答知识性问题、翻译、摘要 基础聊天机器人
L2 工具使用 能调用外部工具获取实时信息 查询天气、搜索网页、读取文档 Function Call 增强的助手
L3 自主规划 拆解复杂目标，制定多步计划，自主选择工具 "帮我分析数据并生成报告"、"帮我重构这个模块" Claude Code（Plan Mode）、Hermes-Agent
L4 多Agent协作 多个Agent分工协作，并行处理，互相审查 一个Agent写代码，一个审查，一个写测试，同时进行 Claude Code（Subagent Mode）、多Agent框架

从 L1 到 L4，本质上是从"被动的知识输出"到"主动的目标执行"的进化。你日常使用的 Hermes-Agent 处于 L3，Claude Code 则横跨 L3 和 L4——既有自主规划能力，也能派出子代理并行工作。

Claude Code 是一个完整的 Agent 实现。把它拆开来看，你就能理解 Agent 各组件在实际产品中是怎么落地的：

🧠

大脑：Claude 大模型

理解你的需求、生成代码、推理分析。就像 Agent 的"CEO"——做所有核心决策。模型越强，Agent 能做越复杂的事。

🔧

工具：文件系统 + 终端 + Git + MCP

读写文件、运行命令、管理版本、通过 MCP 接入数据库/API/外部服务。这是 Agent 的"手"——没有手的 CEO 再聪明也干不了活。

📝

记忆：CLAUDE.md + Memory + 上下文

CLAUDE.md 记录项目知识，Memory 保存持久偏好，对话上下文追踪当前任务。这是 Agent 的"笔记本"——没笔记本的助手每句话都得从头解释。

📋

规划：Plan Mode + TodoWrite

Plan Mode 让 Agent 先设计方案再执行，TodoWrite 追踪每个子任务的完成状态。这是 Agent 的"计划表"——先想再做，不盲目行动。

⚡

执行：读写 + 运行 + Git

在获得批准后，Agent 直接操作文件系统、执行 shell 命令、创建 commit。它是真的在"干活"，而不只是"建议你干什么"。

☑

验证：测试 + 类型检查 + Review

改完代码后自动运行测试、执行类型检查、用 /review 自我审查。这是 Agent 的"质检员"——不写 Bug 代码的关键保障。

🔄

反思：Bug 修复 + /compact + 方案调整

遇到错误时分析原因并改进，上下文溢出时用 /compact 压缩，方案不对时主动调整。这是 Agent 的"自省能力"——真正智能的标志。

Agent 的强大能力是一把双刃剑——能力越强，出错的影响也越大。以下是三个最关键的挑战和应对策略：

👻

幻觉放大

单个回答的幻觉已经挺麻烦了。Agent 执行多步操作时，一步出错可能导致连锁反应——后面的所有步骤都建立在错误的基础上。就像盖房子第一层歪了，后面全歪。

对策：用 Plan Mode 先审方案再执行，关键步骤设置人工确认点，每步完成后检查输出是否符合预期。

📈

上下文溢出

复杂任务可能消耗几万甚至几十万 Token。当上下文太长，Agent 会"忘记"前面的信息，推理质量下降。就像一个人同时记着太多事，效率反而变低。

对策：用 /compact 压缩关键信息，用 Subagent 分流子任务到独立上下文，把大任务拆成多个小会话。

🔒

安全风险

Agent 有文件系统读写权限和命令执行能力——如果被引导执行恶意命令，后果严重。就像你把公司服务器密码给了一个聪明但不够谨慎的新人。

对策：权限最小化原则（只给必要的目录访问）、操作确认机制、关键变更走 Code Review 流程、不在 Agent 中输入密码和密钥。

A2A & Skills

Agent间协作（A2A）与技能系统（Skills）

当单个Agent的能力达到瓶颈，多Agent协作是下一步。A2A定义了Agent之间如何沟通，Skills定义了如何为Agent注入专业能力。

A2A（Agent-to-Agent）由 Google 于 2025 年提出，是一套开放协议，定义了不同 Agent 之间如何发现彼此、交换任务、传递结果。

类比：如果 MCP 是 AI 和工具之间的 USB-C 接口（统一了连接方式），A2A 就是 Agent 之间的 TCP/IP 协议（统一了通信方式）——让不同厂商、不同框架开发的 Agent 能够互相协作，就像一个公司的不同部门即使用不同系统也能通过标准流程协同工作。

🏫

Agent Card（名片）

每个 Agent 公开自己的"能力名片"——描述自己能做什么、接口是什么、怎么调用。其他 Agent 通过这张名片"发现"它，就像在通讯录里找到对口的同事。

📋

Task（任务）

标准化的任务格式，包含目标描述、输入数据、预期输出、进度状态。不管哪个 Agent 接收，看到 Task 就知道"要什么、给我什么、做到哪了"。

📦

Artifact（产物）

任务执行过程中产生的中间结果和最终成果。Artifact 可以是一段代码、一份报告、一个文件——有统一的格式，让上下游 Agent 都能读懂。

当前实际情况 A2A 协议仍在早期发展阶段。目前你日常使用的 Claude Code 和 Hermes-Agent 主要在单个 Agent 层面工作，多 Agent 协作更多通过 Subagent 机制实现。但 A2A 代表的方向是明确的——未来的 AI 工作流一定是多个 Agent 协同完成的。

多 Agent 协作就像一个项目团队的三种工作方式：可以是按流程串行，可以分头并行，也可以互相辩论。选择哪种取决于任务的特性：

🔀

顺序编排（Orchestration）

一个主 Agent 像导演一样按步骤调度不同的专业 Agent。就像流水线：需求分析 Agent → 架构设计 Agent → 编码 Agent → 测试 Agent。

适合：流程化任务，前后步骤有依赖关系。

⇳

并行分发（Parallel Dispatch）

主 Agent 将大任务拆解后同时分发给多个 Agent 并行处理，最后汇总结果。就像让三个工程师同时开发三个微服务。

适合：可并行化的任务，子任务之间相互独立。

⚖

辩论式（Debate/Critique）

一个 Agent 生成方案，另一个 Agent 批判审查，迭代改进。就像代码写手和代码审查者来回过招，直到质量达标。

适合：质量要求高的任务，需要多角度审视。

你已经在用了 Claude Code 的 Subagent 机制就是并行分发模式的实践——Claude 自动判断哪些子任务可以并行，派出多个子代理同时工作。当你看到输出中写着"正在派出子代理去搜索..."，那就是并行分发在运作。

如果你用过 Claude Code，你可能注意到它会"派出子代理去搜索某个信息"——这就是 Subagent 在工作。理解它有助于你更好地使用 Claude Code。

👥

什么是 Subagent

Subagent 是主 Agent 创建的子任务执行者。它有独立的上下文窗口（不被主对话污染），执行完任务后返回结果，然后自动销毁。

三大优势：

  • 上下文隔离——子任务不占用主对话的 Token 配额
  • 并行执行——多个子代理同时工作，速度快
  • 专业分工——不同任务用不同类型的子代理
📚

Subagent 类型

Claude Code 有不同类型的子代理，各司其职：

  • Explore——只读搜索文件和代码符号
  • Plan——设计方案，不写代码
  • General——通用任务，可读写可执行
  • code-reviewer——专项代码审查
  • code-explorer——深度代码库探索
  • code-simplifier——代码简化和重构

常见 Subagent 使用场景

类型 能力范围 典型使用场景
Explore 只读，搜索文件 / 代码符号 "在全项目中找到所有调用旧 API 的地方"
Plan 设计方案，不执行 "先设计用户认证模块的架构方案"
code-reviewer 审查代码质量 "/review 帮我检查最近的改动有没有问题"
General 读写文件、执行命令 "独立实现这个数据处理的小功能"

Skills 是可复用的专业知识包，用来扩展 Agent 能做什么。可以这样理解：Agent 像一个刚入职的聪明新人——智商够，但不懂你公司的规矩和流程。Skills 就是岗前培训手册，教他如何处理特定领域的专业任务。

📄

Skills 是什么

Skills 是 Markdown 格式的专业指导文件，放在 .claude/skills/ 目录下。每个 Skill 包含：触发条件（何时加载）、执行流程（怎么做）、最佳实践（怎么做更好）、注意事项（别踩什么坑）。

Agent 在遇到相关任务时自动加载对应的 Skill，就像你遇到某个工作场景时翻开对应的 SOP 手册。

⚖

Skills vs MCP

很多人搞混这两个概念，其实分工明确：

Skills = 流程指导 + 领域知识
教 Agent "怎么做" 和 "为什么这样做"。

MCP = 工具接口
给 Agent "用什么工具去做"。

两者互补：一个 Skill 可以调用 MCP 工具来完成任务。就像"装修指南"(Skill) + "工具箱"(MCP)。

💎

Skills 的价值

一次编写，团队复用——老员工写一次，新人直接用
操作规范统一——所有人都按同一套流程执行
最佳实践封装——把经验变成可复用的资产
降低使用门槛——新人不需要记住所有细节

你已经接触过 Skills

在 Hermes-Agent 中，skills.zip 就是预打包的专业技能集。在 Claude Code 中，.claude/skills/ 目录存放自定义技能。两者都遵循同样的 Skills 设计理念：将专业领域知识封装成"即插即用"的能力模块，让 Agent 在遇到相关任务时自动获得专业指导。

举个例子 假设你有一个"代码审查" Skill，里面写了：① 检查命名规范 ② 检查空指针 ③ 检查 SQL 注入风险 ④ 检查错误处理是否完善。每次你让 Claude Code 做 Code Review，它自动加载这个 Skill，然后按照里面列出的检查清单逐项审查——而不是凭它自己的"直觉"。这就是 Skills 把隐性经验变成显性流程的价值。

前面讲了 LLM、Function Call、MCP、Agent、A2A、Skills……这么多概念，它们之间到底是什么关系？下面用两条链路帮你串起来：

链路一：一次简单的 AI 对话怎么运作的

用户 → 输入 Prompt → 大模型 (LLM) → 发现需要外部数据 → 触发 Function Call → 通过 MCP 协议连接 → MCP Server（数据库 / 文件 / API）→ 执行并返回结果 → 大模型 整合信息 → 回复 用户

链路二：当任务变得复杂，Agent 如何接管

用户 给出复杂目标 → Agent 接管 → 制定执行计划 → 使用 Function Call / MCP 获取信息 → 派出 Subagent 并行处理子任务 → 验证每个结果 → 迭代修正 → 完成目标，汇报 用户

图：AI技术栈概念层次——下层是上层的基础，每个概念解决不同层面的问题

关键关系小结：

  • A2A 让多个 Agent 能够发现彼此、交换任务、协作完成任务
  • Skills 为 Agent 注入专业领域知识，让它从"通用助手"变成"领域专家"
最后的总结 这些概念不是独立的——它们共同构成了现代 AI 应用的技术栈：LLM 提供智能，Prompt 引导方向，Function Call 赋予行动力，MCP 标准化工具接入，Agent 实现自主执行，A2A 连接多 Agent 协作，Skills 注入专业知识。你不需要一次性记住所有概念，先理解它们各自的定位，在日常使用中再慢慢体会。
